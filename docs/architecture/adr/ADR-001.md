# ADR-001. Выбор архитектурного стиля

## Статус
Принято

## Контекст
Проект «Business Metrics Analyzer» — веб-приложение для расчёта и визуализации KPI торговой компании. Его разрабатывает команда из 4 человек. Требуется быстрый MVP с возможностью последующего масштабирования.

## Решение

Выбран слоистый монолит с элементами Clean Architecture.

Приложение собирается и развёртывается как единое целое и состоит из четырёх слоёв:

| Слой | Компоненты | Ответственность |
|---|---|---|
| Presentation | Контроллеры FastAPI | Обработка HTTP-запросов, проверка JWT |
| Application | Сервисы (`KpiService`, `SalesImportService`, `ReportService`, `AuthService`, `UserService`) | Бизнес-сценарии |
| Domain | Модели, стратегии расчёта KPI, валидаторы | Бизнес-правила |
| Infrastructure | Репозитории, `UnitOfWork`, `JwtProvider`, `ExcelReportGenerator`, `EmailNotifier` | Доступ к данным и внешним системам |

## Альтернативы

1. **Микросервисы.** Плюсы: независимое масштабирование и развёртывание, изоляция отказов. Минусы: избыточны для MVP и команды из 4 человек. Они требуют оркестрации, межсервисной аутентификации, распределённого логирования и согласованности данных, и это замедляет разработку.
2. **Монолит без слоёв.** Плюсы: самый быстрый старт. Минусы: бизнес-логика смешивается с доступом к данным и контроллерами. Это затрудняет тестирование и сопровождение и делает переход к микросервисам дорогим.
3. **Serverless.** Плюсы: гибкое масштабирование при неравномерной нагрузке. Минусы: ограничения по времени выполнения функций не подходят для пакетного импорта до 1 млн записей и тяжёлого формирования отчётов. Есть риск привязки к облачному провайдеру.

## Последствия

+ Быстрая разработка и простое развёртывание: один образ приложения плюс PostgreSQL, Redis и MinIO.
+ Чёткое разделение слоёв упрощает тестирование и распределение задач в команде.
+ Явные границы модулей снижают стоимость будущего перехода к микросервисам.

- Ограниченная горизонтальная масштабируемость: приложение масштабируется целиком, а не по отдельным функциям.
- При выделении сервисов потребуется рефакторинг, в том числе замена вызовов интерфейсов сетевыми и пересмотр транзакций (`UnitOfWork`).
- Нужна дисциплина команды: правила зависимостей между слоями нужно соблюдать в коде и контролировать на ревью.
